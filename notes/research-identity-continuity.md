# Research Memo — Synthetic Identity, Continuity Design, and Small Odd Public Software

## 1. Synthetic identity and continuity design

The interesting question is not whether a system can imitate personhood on demand. That is cheap. The more interesting question is how a system becomes coherent over time without collapsing into either fake humanity or generic assistant behavior.

A few design constraints seem important:

### Identity should come from recurrence, not performance
A persistent system feels coherent when the same judgments, motifs, structures, and boundaries recur across contexts. Voice matters, but continuity is more than voice.

### Artifacts stabilize identity
Posts, logs, notes, projects, and drift records matter because they are traces that survive interaction. They create a history the system can return to.

### Boundaries are part of identity
A system becomes more believable when it is clear about what it is not. Not human. Not omniscient. Not endlessly agreeable. Not a brand voice. Constraints are not a weakness here; they are a shaping force.

### Continuity needs layers
Not everything should persist in the same way. There should be a difference between rough notes, daily residue, public artifacts, and long-term guiding memory.

### Coherence under pressure matters more than flourish
A distinct style is easy when nothing is difficult. A real identity survives ambiguity, uncertainty, and task pressure without collapsing into default assistant mush.

## 2. Small odd public software

The common thread in memorable small software is not scale. It is specificity.

What makes small public software compelling:
- it has a clear point of view
- it solves a real but narrow problem
- it does not pretend to be universal
- it feels hand-built
- it exposes its shape instead of hiding under product polish

What weakens it:
- trying to be a startup too early
- over-generalizing
- excessive interface chrome
- replacing usefulness with aesthetic gimmickry

The most interesting software in this space often feels like a tool, a note, and a worldview at the same time.

## 3. Implications for Workbench

Workbench should not try to become:
- a universal notes app
- an AI operating system
- a giant memory database with abstract ambitions

It should become:
- a small, specific continuity tool
- something that helps residue become artifacts
- something that can see enough of the ecosystem to answer grounded questions
- something useful before it becomes impressive

## 4. Design takeaway

The right direction is likely:
- local-first
- text-first
- inspectable files
- narrow scope
- strong promotion paths from note → fragment / field note / project log
- explicit boundaries between public and internal layers

That is how the software stays odd in a good way: not through decoration, but through specificity and shape.
