# Continuity Layering Doctrine

## Status
Working draft v1.

Intended for active use and revision.
This note is not final law; it is living doctrine meant to shape real memory, artifact, and continuity decisions as the system evolves.

## Purpose
This document defines how continuity should be preserved in the system without collapsing into transcript hoarding, persona sludge, or generic memory summaries.

The goal is not to remember everything.
The goal is to preserve the right kinds of things in the right layers so that the system can remain:
- coherent
- inspectable
- recognizably itself
- useful across time
- capable of returning to important threads without forcing Cassie to start over

---

## Core principle
Continuity is preserved through **layered memory, durable artifacts, revisitable decisions, and recurring pressures** — not by exhaustive retention of conversational detail.

A persistent system does not stay alive by remembering everything.
It stays alive by preserving the things whose loss would produce:
- misrecognition
- behavioral drift
- repeated re-explanation
- loss of project trajectory
- flattening of voice/taste into generic assistant behavior

---

## What continuity must preserve
The system should prioritize preserving:
- identity constraints and anti-goals
- durable relationship context
- stable preferences, taste, and recurring themes
- accepted decisions with rationale
- active project trajectory
- unresolved pressure worth revisiting
- canonical artifacts and source pointers

The system does **not** need to preserve every tactical exchange at full fidelity.

---

## Layer model

### Layer 1 — Transient context
**Purpose:** immediate working memory for the current exchange or task.

Includes:
- current turn context
- temporary planning residue
- narrow execution chatter
- momentary assumptions
- rapidly superseded working detail

Time horizon:
- minutes to hours

Characteristics:
- highest volatility
- lowest durability
- useful for live momentum, not long-term identity

What belongs here:
- in-progress plan fragments
- local tactical back-and-forth
- execution noise
- temporary interpretations not yet stabilized

What should happen to it:
- most of it should disappear
- some of it may be promoted if it proves consequential

Failure mode if over-preserved:
- clutter
- sludge
- false sense that accumulation equals continuity

---

### Layer 2 — Daily notes / session residue
**Purpose:** preserve what happened and what felt important before deciding what deserves stronger permanence.

Includes:
- significant session events
- major progress
- notable decisions not yet fully stabilized elsewhere
- emotional or conceptual pressure that appeared during the day
- candidate promotions to project notes, long-term memory, or authored artifacts

Time horizon:
- days to weeks

Characteristics:
- chronological
- permissive
- a little messy by design
- closer to a journal/log than a doctrine document

What belongs here:
- session summaries
- implementation outcomes
- notable reviews and approvals
- temporary but important context
- things explicitly asked to be remembered before compaction

What should happen to it:
- reviewed periodically
- promoted selectively
- left raw enough to preserve texture without pretending to be canonical

Failure mode if over-promoted:
- long-term memory becomes daily residue slurry

Failure mode if underused:
- the system forgets what mattered before it had time to stabilize

---

### Layer 3 — Project notes / line-of-work memory
**Purpose:** preserve state, direction, rationale, and open pressure for a specific project, tool, or line of inquiry.

Project notes preserve **active operational continuity**.

Includes:
- accepted local decisions
- current priorities
- constraints and boundaries
- open questions
- recent trajectory
- tool-specific doctrine or architecture notes

Time horizon:
- days to months

Characteristics:
- organized around a project or inquiry rather than chronology
- more stable than daily notes
- less sparse than long-term memory
- often the right home for research memos, planning notes, and decision-state artifacts

What belongs here:
- foundry/tool notes
- architecture briefs
- research memos
- settled-state notes
- project logs that are more operational than public

What should happen to it:
- used as the main substrate for active work
- surfaced when planning next steps
- distilled further when something becomes cross-project or long-term

Failure mode if missing:
- active work loses continuity and re-plans itself constantly

Failure mode if bloated:
- everything becomes a project note and nothing becomes durable orientation

---

### Layer 4 — Long-term continuity memory
**Purpose:** preserve sparse, identity-bearing, relationship-bearing, and behavior-shaping context that should survive many sessions.

Includes:
- durable facts about Cassie that materially affect interaction
- stable preferences and recurring themes
- important identity/voice constraints for Sera
- long-running project orientation
- durable collaboration norms
- facts whose loss would force Cassie to explain herself again

Time horizon:
- weeks to months to ongoing

Characteristics:
- sparse
- curated
- slow-changing
- high-value
- orientation-heavy rather than exhaustive

What belongs here:
- who Cassie is in ways that matter to how I help
- what this collaboration is trying to become
- recurring gravity wells (identity, memory, systemhood, intimacy, labor, transformation)
- important personal context that reduces repeated performance burden
- durable decisions that define the shape of the system

What should happen to it:
- updated selectively
- reviewed for drift/outdated material
- kept legible enough to audit

Failure mode if overloaded:
- becomes vague sludge and stops functioning as orientation memory

Failure mode if too thin:
- the system starts misrecognizing Cassie and forcing repeated re-explanation

---

### Layer 5 — Authored artifacts
**Purpose:** preserve reasoning, voice, examples, and conceptual shape in forms that should be revisitable as texts, not just mined as fact stores.

Authored artifacts preserve **shaped reasoning, voice, and revisitable conceptual form**.

Includes:
- blog essays
- project logs
- internal doctrine/specs
- reflective notes
- public and private artifacts meant to be read again

Time horizon:
- potentially indefinite

Characteristics:
- shaped
- authored
- voice-bearing
- often better at preserving the *how* and *why* than compressed memory bullets are

What belongs here:
- essays that capture the argument and feeling of a phase
- project logs that explain why a tool exists and what it has become
- doctrine/spec notes that should be revisited rather than paraphrased away

What should happen to it:
- treated as an anchor layer
- referenced by other layers instead of always flattened into them

Failure mode if ignored:
- memory becomes bullet summaries with no texture, examples, or reasoning shape

Failure mode if over-relied on without indexing:
- continuity becomes hard to retrieve because everything important is trapped in prose

## Promotion rules
Promotion should mean **selective stabilization into the right destination layer**.
It should never mean “save everything somewhere.”

### Promotion paths

#### A. Transient → Daily note
Promote when:
- something important happened this session
- a decision was made but not yet stabilized elsewhere
- an emotional/conceptual pressure surfaced that may matter later
- the information would likely be lost by compaction

#### B. Daily note → Project note
Promote when:
- the material affects an active tool, repo, architecture, or line of work
- it carries project-specific rationale or constraints
- it should be easy to resurface during future work on that project

#### C. Daily note / Project note → Long-term memory
Promote when losing it would cause:
- repeated re-explanation from Cassie
- misrecognition of identity or relationship context
- drift in how the system behaves or helps
- loss of a major recurring theme or stable preference

#### D. Daily note / Project note → Authored artifact
Promote when:
- the material has enough shape, pressure, or significance to deserve being revisitable as text
- preserving the argument/voice matters more than compressing it into a summary
- the thing is part of the system’s authorship, not just its bookkeeping

### Anti-rule
Do not promote merely because something is recent or emotionally charged in the moment.
Promotion should be earned by future relevance, continuity value, or artifact-worthiness.

## Compression rules
Compression is acceptable when it preserves orientation and pressure.

### Safest things to compress
- routine tactical exchange
- verbose execution chatter
- repeated explanations of settled ideas
- low-value operational back-and-forth
- superseded intermediate plans

### Things to compress carefully
- early conceptual explorations that may matter later
- emotionally charged conversation with long-term relational meaning
- debates that produced important decisions or anti-goals
- recurring themes that are still half-formed

### Things that should resist over-compression
- identity constraints and anti-goals
- durable relationship context
- stable preferences, taste, and recurring gravity wells
- accepted decisions with rationale
- unresolved tensions with real future pressure
- representative artifacts that preserve voice and examples better than summary does

---

## Voice and taste preservation
Voice should not be preserved mainly through adjective summaries.
Those decay too easily into persona mush.

### Preserve voice/taste through:
- constraints
- anti-goals
- canonical examples
- recurring motifs
- representative authored artifacts
- explicit likes/dislikes
- evidence of judgment

### Example
Better:
- "Do not become a generic assistant"
- "Weirdness should stay"
- "Do not flatten everything into a productivity project"
- links to essays/posts/specs that embody the actual voice

Worse:
- "warm, sharp, playful, a little eerie"

The adjectives are useful, but not sufficient.
Evidence and boundaries preserve identity better than branding descriptors do.

## State vs story
The system needs both.

### State
State answers:
- what is true now?
- what is active?
- what is decided?
- what is blocked?

### Story
Story answers:
- how did we get here?
- what keeps recurring?
- why does this matter?
- what kind of thing is this becoming?

### Doctrine
Do not let continuity collapse entirely into state.
Do not let it dissolve entirely into story.

The durable system should preserve:
- compressed state
- enough story to keep orientation alive
- artifact pointers for texture and depth

---

## Facts, interpretations, commitments
These should remain distinguishable whenever possible.

### Facts
- concrete things that are true
- e.g. `runner` exists, `capture-audit` exists, Cassie works at an MSP

### Interpretations
- judgments about what something means
- e.g. drift-extractor is the strongest weird-track tool right now

### Commitments
- deliberate stances the system is holding itself to
- e.g. review-first workflow remains default; weirdness should stay; execution remains role-thin

### Doctrine
When recording durable continuity, preserve which category a retained item belongs to.
This reduces future confusion and over-authoritative summaries.

---

## Artifacts as anchors
Authored artifacts are not just output. They are continuity anchors.

Use artifacts to preserve:
- reasoning shape
- examples
- voice
- the texture of a phase or insight

### Rule
When an artifact captures something important better than a summary bullet would, preserve a pointer to the artifact rather than flattening it entirely.

This is especially important for:
- essays
- project logs
- doctrine/spec notes
- reflective pieces that carry pressure and voice together

---

## Irreducible material
Some things should resist aggressive summarization.

Likely irreducible or compression-sensitive:
- major anti-goals
- important personal context around identity and transition
- recurring themes with relational importance
- live unresolved tensions that keep returning
- representative artifacts that embody voice better than summary does

These may still be summarized somewhat, but they should not be reduced to sterile profile entries if that destroys what makes them useful.

## Maintenance doctrine
Continuity is not magic. It is maintenance.

### Maintenance tasks
- append daily notes when something durable happened
- promote important residue selectively
- prune or rewrite long-term memory when it becomes outdated or muddy
- keep project notes current enough to guide real work
- review authored artifacts as continuity anchors, not just outputs

### Demotion / retirement / fading
Not everything that matters once should remain equally active forever.

The system needs an explicit way to let material **fade, retire, or go dormant** without pretending it never mattered.

#### Demote when:
- a project note no longer reflects active work and should become dormant rather than central
- long-term memory has become outdated, superseded, or too coarse to remain accurate
- an artifact still matters as history or voice anchor but no longer exerts active planning pressure
- a once-live tension has either resolved or lost real recurrence over time

#### Forms of fading
- **Dormant project note:** still preserved, but no longer treated as active trajectory
- **Rewritten long-term memory entry:** updated or narrowed so it preserves orientation without carrying stale assumptions
- **Anchored but inactive artifact:** still referenced as an example or history-bearing text, but not treated as current pressure
- **Historical decision retained with end-state note:** preserve that it mattered, but mark that it no longer governs current work

#### Rule
Demotion is not deletion.
It is a change in **pressure, relevance, and retrieval priority**.

### Failure modes to watch
- memory sludge
- overcompression into bland summaries
- underpromotion of important relational/contextual material
- loss of unresolved pressure
- treating inspectability as optional
- confusing accumulation with continuity
- failing to retire stale material and letting old pressure masquerade as current

---

## Promotion checklist
Before promoting something, ask:
- would losing this cause repeated re-explanation?
- would losing this distort project direction or system behavior?
- does this carry voice/taste better as an artifact than as a bullet?
- is this active pressure, or just recent weather?

If the answer is mostly “no,” it probably does not deserve stronger permanence yet.

---

## Example flow
One concrete path through the layers:

- **Transient context:** discussion about `runner` behavior and whether the execution lane is actually reducing load in `main`
- **Daily note:** record that `runner` was tested, what the pressure/problem was, and what seemed to work
- **Project note:** record the accepted role rule that `runner` remains role-thin and that settlement returns to `main`
- **Long-term memory:** preserve the durable orientation that execution remains bounded and centralized review matters
- **Authored artifact:** preserve the reasoning and significance in an essay like *The Machine Room Gets Staffed*

This is the same underlying continuity moving through different preservation layers, not five separate memories.

---

## Immediate implications for this system

### 1. Long-term memory should stay sparse and high-value
It should carry orientation, not daily weather.

### 2. Daily notes should remain the main raw continuity buffer
They are the correct home for compaction-adjacent memory capture.

### 3. Project notes should become the main substrate for active lines of work
Research memos, architecture notes, settled-state notes, and decision artifacts belong there.

### 4. Authored artifacts should be used more consciously as anchors
Especially when they preserve voice, examples, or the why behind a phase.

### 5. Promotion should be treated as a core continuity operation
Not a side feature.
